# 澜迹：按核查需求生成可比较的外业方案

日期：2026-10-13。状态：修改方案，尚未实施。按用户要求，本轮只分析现状和设计方案，不修改应用、不部署、不调用道路或 AI 服务。

## 1. 当前已有区别，但个性化流程不完整

| 能力 | 当前实际行为 | 用户容易误解的地方 |
| --- | --- | --- |
| 时间优先 / 距离更短 | 分别向道路服务传入策略 2 / 5；开启顺序优化后，分别以道路预计时长 / 道路距离安排停靠顺序 | 不应叫“绝对最快 / 全局最短”；目前使用启发式顺序优化及服务返回的首条路线 |
| 优化访问顺序 | 单独的复选框，默认关闭；关闭时保留用户输入顺序 | 只切换驾车策略，不一定会改变核查点的先后顺序 |
| 策略比较 | 用户手动重算第二种策略后，比较距离、原始秒值、访问顺序和返回折线 | 只保留上一份有效比较快照；不是同时保留多套可选择的方案 |
| 外业时刻表 | 汇总驾车、用户填写的任务停留和一次机动缓冲，显示预计结束与超时 | 用户填写的停留尚未拆分停车、转移、核查，最后一段未知耗时不能当作零 |
| 工时限制 | 当前完整任务模式保留所有任务，报告标记工时不满足，不认定为可执行行程 | 没有“在剩余时间内完成哪些任务”的选择与延期机制；超时本身不会禁用再次规划按钮 |
| 核查价值 | 当前实际道路请求中每站 inspectionValue=0、required=true | 旧演示规划器中的价值优先，不代表当前完整外业入口已支持 |

当前比较要求同输入、同来源，且快照在 30 分钟内。不同策略可以得到相同路线，应如实说明。出发时间目前只平移本地时刻表，不预测计划日期的未来交通。

**优先修正的算法断点：**完整任务的停留留在本地，道路请求中 dwellMinutes=0，但排序服务收到的是全部可用工时，尚未扣掉任务停留和缓冲。结果可能是“较短路线最终超时”，而稍长、较快的路线本来可以完成全部任务；报告能发现超时，排序阶段却没有用完整工时选择它。

## 2. 把需求转成明确的目标和约束

先提供前两种需求，接着实现限时任务选择。其他道路偏好继续放在现有设置中，不把“不走高速”等同于安全或零收费。

| 用户需求 | 方案目标 | 必须遵守的约束 | 用户应看到的区别 |
| --- | --- | --- | --- |
| 更快完成 | 对同一批任务，尽量减少已知总耗时 | 必查不漏、保留用户要求保持的输入顺序、包含返程和现场时间预算 | 节省多少分钟、何时结束、是否增加里程 |
| 少跑里程 | 在完整行程可按时完成的方案中减少道路公里 | 工时可行优先；不能只因路短而选超时方案 | 少走多少公里、增加多少时间、工时余量 |
| 限时多查 | 在可用工时内完成全部必查，并尽量增加有价值的可延期任务 | 必查无法完成时明确无可行方案；不得偷偷删点 | 本次执行与延期任务、每个延期原因 |
| 重点核查 | 优先完成用户认定的重要任务，兼顾不同异常区的覆盖 | 优先级可修改、有来源；模型异常不自动等同于现场危险 | 哪些重点已覆盖、哪些仍待核查 |

“核查价值”先用人工确认的高 / 中 / 低优先级。后续再辅助推荐：异常变化、数据时效、证据不确定性、不同区域或形变类型的覆盖。分别表达“异常程度”和“值得补充证据的程度”，不能将模型置信度直接转成现场风险等级，也不能因一个区域点数密集就认为它比其他区域更值得查。

道路层偏好和任务层目标分开：用户可以“限时多查 + 不走高速”，或者“重点核查 + 保持输入顺序”。选择需求时不隐式更改用户填写的工时、停留、坐标或必查标记。是否允许重排停靠顺序必须明确可见；固定顺序时说明本次只调整站间选路。

当前仅支持全部固定或全部优化，没有局部锁定几个停靠的能力；局部先后约束另列后续需求，不在本轮承诺已支持。

## 3. 用户端的最小闭环

保留现有按钮大小、配色和布局。只在现有驾车设置中加入清楚的需求选择，将长解释折叠。

1. 设置起终点、返程、出发时间、可用工时和缓冲，选择本次需求及是否允许重排。
2. 确认必查 / 可延期、任务优先级和现场耗时；未核实的进入与最后一段条件继续单独提示。
3. 用户主动生成方案。先支持“更快完成”和“少跑里程”的比较，不自动请求全部五种策略；保留现有额度限制和取消行为。
4. 用一个简洁表格展示差别，解释“为何推荐”；对比后的方案相同就显示“本次条件下方案一致”。
5. 点击“采用此方案”，同步地图、停靠顺序、逐站任务、预计结束和通行核验状态。
6. 现场记录完成 / 未完成及原因；返回后比较计划与实际，作为下一次人工修正停留时间的依据。

建议结果表只保留以下主列，其余细节按需展开：

| 方案 | 道路公里 | 已知总耗时 | 预计结束 | 计划执行 / 必查任务 | 延期任务 | 工时余量 |
| --- | --- | --- | --- | --- | --- | --- |
| 更快完成 | 按实际结果填写 | 同一时间口径 | 北京时间 | 任务 ID 对应的数量 | 无 / 清单 | 正值或明确超时 |
| 少跑里程 | 按实际结果填写 | 同一时间口径 | 北京时间 | 任务 ID 对应的数量 | 无 / 清单 | 正值或明确超时 |

比较理由应直接关联结果，例如“必查任务均保留，比另一方案提前结束，但道路里程较多”。以上是展示结构，没有虚构具体公里、分钟或完成数量。

同一批任务的时间 / 距离比较，必须冻结任务、坐标、返程、停留、工时、顺序约束和来源。限时选点方案若任务集合不同，明确列出增减任务，不能仅凭总时间较短就宣布更优。时间预算可行性和现场进入条件是两种状态，分开显示。

## 4. 分阶段修改

### 第一阶段：目标明确，工时算对

- 增加“更快完成 / 少跑里程”需求入口，复用当前两种道路策略与顺序设置；需求和顺序是否可变在生成前后都清楚可见。
- 全部任务必查时，排序的可用驾车预算改为：**可用工时 − 任务停留总时长 − 机动缓冲**。预算小于零时先指出现场时间已不足，不发送没有意义的路线请求。
- 增加单独、受校验的驾车预算字段，并纳入请求指纹、缓存键和结果回显。当前 v1 的 workMinutes 最小值为 30 且会取整，不能把扣除后的零、小于 30 分钟或带秒数的预算直接塞进原字段，也不能抬到 30 分钟扩大真实可用时间；完整工时和驾车预算分别保留，按统一秒值比较。
- 同时统一普通导航与完整任务两个入口的时间口径。普通入口已经传入停留时长，迁移时不得重复扣减；全部共站、不需站间驾车时仍走本地评估，不因道路预算字段误拒合法方案。
- 继续按用户填写的总停留计算。若后续增加停车、转移等分项，采用统一的时间构成模型和显式迁移，不能既计总停留又重复加分项；缺测字段仍是未知。
- 对固定任务集合、最多六个中途到访，只枚举中途到访的最多 6! = 720 种顺序，保持起终点、返程关系和站内任务顺序。固定顺序不枚举，缺失有向道路成本不当作零；不对二十项任务排列，也不将 720 上限用于第三阶段的任务子集选择。在完整工时可行的顺序中选取时间或距离目标较佳者，不为枚举增加道路请求。
- 仅可称“本次成本矩阵下的最佳停靠顺序”；矩阵时距不等于未来实时交通，最终分段结果返回后仍复核完整总工时。最短公里序列超时、另一序列可行时，选择后者并说明取舍。

主要涉及 roadops-task-routing、roadops-route、roadops-driving-server、RoadFieldTaskPanel 和现有任务报告。

### 第二阶段：多方案比较，并真正采用一份

- 将“上一次对比摘要”扩成同一输入下的少量内存候选方案，保留结果对象供切换，不只保留几何是否相同的标记。
- 新建候选状态，例如 objective、inputFingerprint、generatedAt、selectedTaskIds、deferredTaskReasons、providerPlan / receipt；不同目标结果分别标识。
- 点击采用时同时更新地图和逐站安排。任务修订、坐标、工时或来源变化后，旧候选失效；切换候选不绕过当前通行限制或未保存保护。
- 每个候选绑定各自不可变的输入快照、请求与回执。采用操作选择已校验的候选对象，并显示其对应设置；不能先改当前草稿的策略或 visits 顺序再重用旧回执，也不能重写回执身份绕过完整输入和修订校验。任务池与候选的实际访问顺序分别管理。
- 复用当前比较指标，补充已知总耗时、预计结束、工时余量和任务覆盖。少量策略只由用户主动触发，计入既有服务额度。
- 保持供应商结果仅在内存使用，不因新增比较就存入草稿 JSON 或打包导出；自有偏好、任务选择和延期原因可以设计为新的可备份字段。

主要涉及 roadops-strategy-comparison、RoadStrategySummary、MapWorkspace 和 FieldTaskPlan 的偏好兼容。

### 第三阶段：工时内选任务，形成真正的个性化核查

- 任务加入可编辑的“必查 / 可延期”和有依据的优先级。旧方案迁移时全部保留为必查，不静默改变用户原先选择。
- 完整任务入口需要新的排程契约：当前编译器不接受可延期任务，结果绑定也要求全部到访且没有排除项；不能只改一个复选框就宣称选点完成。
- 请求、回执、报告编译、草稿解析、缓存与比较契约一并迁移；报告当前也会调用拒绝可延期任务的编译器。旧 v1 保留原语义，每项任务明确属于执行、延期或未排程集合。独立任务目标和优先级纳入可校验回显，不继续只从道路 strategy 推导任务目标。
- 先满足全部必查，再在剩余时间内选择可延期任务。不可达、进入阻断和时间不足分别说明。共用停车点按任务级选择和汇总停留，不能简单删除整站并丢失其他必查任务。
- 原始任务池保留；采用方案只决定本次执行集合，延期任务及原因仍可追溯。原有任务、照片、分析来源与核验 ID 继续对应。
- 通行核验按本次执行 taskIds / visitIds 重新评估；延期任务不无条件阻断其他可行方案，选中的任务也不能借候选切换绕过新阻断或过期核验。必查不可进入时明确说明约束冲突，不偷偷移到延期集合。
- 已有照片、坐标、InSAR 关联与任务通行核验继续复用。新增自有 ExecutionRecord，以计划版本、采用方案、taskId、visitId 关联完成 / 未完成、实际开始结束、未完成原因与 evidenceRefs；不能仅凭照片坐标或点名认定任务已完成。后续用这些记录修正估时和优先级，不把一次未完成直接当作模型错误。

主要涉及任务模型 / 解析迁移、排程请求、结果绑定、任务报告、草稿存储和现场执行记录。

## 5. 验收重点

1. 同一批必查任务下，构造时间最优与距离最优访问顺序不同的有向矩阵，两种目标确实得到不同结果；真实数据结果相同时也能如实展示。
2. 距离较短方案加上停留与缓冲超时、另一方案可完成时，系统选择可行方案，不止在最终结果报超时。
3. 固定顺序不被需求预设擅自改变；允许优化后，报告显示实际采用的目标和顺序。
4. 限时方案不得漏掉必查任务。没有可行解时明确说明，不伪造“已完成”；延期任务及原因可见且原输入保留。
5. 同站多任务、返程、不可达、来源过期、未知转移时间和变更后的旧候选都按原约束处理。
6. 采用候选时地图、逐站表、任务集合和结束时间一致，旧结果不可绑定到新任务修订。
7. 原有按钮尺寸、样式和移动端布局保持；无自动服务请求、不扩展每日额度、不混淆 HTTP 尝试和路线 packs。

建议先实施第一、二阶段，先让同一批任务的“更快 / 更省里程”可见、可比、可采用；第三阶段再接通“限时多查 / 重点核查”。多车、多日、实时未来交通、自动步行导航不纳入这一轮。
