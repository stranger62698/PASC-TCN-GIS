## 核心交付

`app/lib/roadops-task-routing.ts` 新增两个无网络、无存储副作用的函数：

- `compileFieldTaskRouting`：FieldTaskPlan → 物理车辆停靠请求 + 本地任务/到访映射。多个任务共享同一次到访只生成一个路由点。运输短 ID 不改写原始 taskId / stopId / visitId；备注、任务目标和核验状态不进入请求。
- `bindFieldTaskRoute`：验证完整逐段响应，按访问实例绑定真实有向 leg，而不是按物理 stopId 去重。保留原供应方生成时间；几何只在内存中使用，不加入 FP1 草稿或 JSON 备份。

A→B→A 中，v1 服务请求只有 A/B 两个物理点，首尾的访问 ID 不同。AB 和 BA 必须分别有结果，缺少任一段即拒绝整体结果。对于“同一个明确 stopId、无需站间驾车”的任务，返回 `no_station_driving` 和空请求；不生成零距离供应商成功结果。

未明确共站的同坐标点、六位小数归一化后重合点均拒绝，不自动归并。除最终返程外的重复中间停靠当前 v1 服务不能表达，明确拒绝，不消除用户到访。完整重复访问能力仍属于 FP2 后续工作，G2-03 不能提前标通过。

## 停留时长与安全边界

v1 服务每点停留上限 180 分钟且会取整，不能直接承载一站多个任务的合计。因此新适配器把运输请求的 dwell 设为 0，单独精确保留全部任务耗时，在本地回执中计算：

`总时间 = 各有向路段秒数 / 60 + 所有任务人工耗时 + 全局缓冲`

包括首次驻点作业与返回后作业，各计一次；小数耗时不四舍五入截断。共享三任务各 180 分钟保留为 540 分钟，不压成 180。当前任务集合固定、停留为与顺序无关的常量，因此运输顺序优化仍只比较驾驶耗时；时窗/最后一段分项排程尚未实现。

回执始终为 `accessStatus=needs_review`，另列 overtime，绝不把供应商 `ready` 当作外业可出发/可进入。明确禁入、缺坐标、尚不支持的可延期任务/计划日期会在发请求前拒绝。到达与离开端点按各次访问分别保留，不能把物理点最大偏移当作每次访问的现场通行核验。

## 独立审查指出的旧模块限制

1. `parseNavigationResponse` 要求 stopOrder 全唯一；原单程防重复守卫保留，新核心独立验证首尾重复的合法返程。
2. `roadops-field.ts` 当前按“ID 等于首站”清零耗时，会丢失返回后的驻点作业。不能将新核心直接接旧报告。
3. v1 `fieldAccess` 每个物理点只有一个最大偏移记录，不能等同到达/离开两次访问的依据。
4. `NavigationDraft` 本身仍不能表示多个任务共享到访；新增完整编辑器直接消费 FieldTaskPlan。旧入口恢复复杂草稿会切入该编辑器，不通过旧适配器压成一个目标。

## 页面与异步边界

- 新报告按到访依次累计任务，含首次驻点及返回后任务；分别显示到达/离开偏移、工时超量、最后一段未知和路线生成时效。所有入口/停车仍待核验，无 ready/safe 认证。
- 地图只画绑定的供应商有向道路分段；同坐标起/返聚合但不丢访问身份，保留全部目标标记。删除停车到目标的虚构连接线，不伪造步行路径。
- 入参变更清除旧报告/路线，用户再手动规划；这是 FP2 保守失效策略。局部排程无请求刷新/路由指纹分离仍属 FP4，不承诺任意本地字段修改均可保留旧几何。
- 自动保存只保存用户白名单；精确内容不变的保存/另存元数据可在内存中重新绑定既有回执。进行中请求遇到先前开始的自动保存，延后元数据回写至结果绑定/失败后，不取消已计费请求。晚到保存不覆盖新输入；恢复/import guard 在提交后同步检查。
- 复用 frontend-design 的既有蓝字、浅蓝底和紧凑分区，不新增第二套主题或更改 InSAR 数据语义色。
